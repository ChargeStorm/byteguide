\subsection{DataTransfer.req in OCPP 1.6 JSON RPC Framework}
\label{sec:datatr-ocpp-1.6}

The listings showing the JSON messages, later on, shall all go into the
\lstinline{Payload} field of the \lstinline{DataTransfer.req} or
\lstinline{DataTransfer.conf} message structures below.

\begin{lstlisting}[language=json,caption={OCPP 1.6 JSON RPC Call message structure},captionpos=t]
[<MessageTypeId>, "<UniqueId>", "<Action>", {<Payload>}]
\end{lstlisting}

The payload of the \lstinline{DataTransfer.req} is:
\begin{lstlisting}[language=json,caption={OCPP 1.6 Payload of DataTransfer.req},captionpos=t]
{
  "vendorId": "",
  "messageId": "",
  "data": ""
}
\end{lstlisting}
Note that in the messages where the data field consists of a JSON payload, all
\lstinline{"} has to be escaped.

\begin{lstlisting}[language=json,caption={OCPP 1.6 JSON RPC CallResult message structure},captionpos=t]
[<MessageTypeId>, "<UniqueId>", {<Payload>}]
\end{lstlisting}


\subsection{Availability of CTEK E-Mobility AB's custom DataTransfer.req}
\label{sec:availability-ctek-e}

From the FW release \verb|ccu_R3.11|, the charging station reports which
\verb|DataTransfer.req|s are available and which are activated by two custom
configuration keys:
\begin{itemize}
\item \verb|CustomizationCtrlEnabled|
\item \verb|CustomizationCtrlSupported|
\end{itemize}

\verb|CustomizationCtrlSupported| details which of the extensions that the
charging station is aware of (i.e.\ has FW support for). For
\verb|DataTransfer.req| that are only sent from the CSMS to the charging
station, no further action are required.

\verb|CustomizationCtrlEnabled| lets the CSMS activate specific
extensions. This is required for all extensions (\verb|DataTransfer.req|) that
are initiated by the charging station (as otherwise it's quite likely that the
CSMS doesn't understand the sent \verb|DataTransfer.req|).

\section{License}
\label{sec:license}

The availability of the messages in this section is seen by
\verb|se.chargestorm.license| in \verb|CustomizationCtrlSupported|. It's not
necessary to activate these in \verb|CustomizationCtrlEnabled|.

The DataTransfer in this section is available on the CCU without any special
configuration.

To install a license.ini file, the CSMS (backend) needs to be able to both
calculate the SHA256 checksum as well as the base64 encoded version of the
content.

\begin{lstlisting}[language=json,caption={DataTransfer.req for LicenseInstall
sent to the CS},captionpos=t]
{
  "vendorId": "se.chargestorm",
  "messageId": "LicenseInstall",
  "data": "{
    \"hash\": \"<SHA256-hash of license.ini\>",
    \"license\": \"<Base64 encoded license.ini>\"
  }"
}
\end{lstlisting}


\subsection{Response}
\label{sec:response}

Upon a successfull installation, the CS will respond with:
\begin{lstlisting}[language=json,caption={DataTransfer.conf for LicenseInstall
sent from the CS},captionpos=t]
{
  "status": "Accepted"
}
\end{lstlisting}

If something goes wrong, the response will be:
\begin{lstlisting}[language=json,caption={DataTransfer.conf for LicenseInstall
sent from the CS},captionpos=t]
{
  "status": "Rejected",
  "data": "{\"reason\: \"<reasoncode>\", \"chargePointSerialNumber|": \"<serialno>\"}"
}
\end{lstlisting}
where \verb|reasonCode| can be any of:
\begin{description}
\item[could not write to license.ini]
\item[could not write  to file] Try again after a hard reset. If it still
  doesn't work, it's likely a corrupted flash or file system.
\item[hash mismatch]
\item[chargePointSerialNumber was not found in license!] The CS's serialno, as
  sent in the field \verb|chargePointSerialNumber|, isn't found in the license
  file to be installed.
\item[could not validate signature of license!]
\end{description}
The field \verb|chargePointSerialNumber| is omitted in all cases except when
stated above.

\subsubsection{Install a \nanogrid\ file}
\label{sec:inst-nanogr-file}

To install a \nanogrid\ configuration file, the CSMS (backend) needs to be able to
both calculate the SHA256 checksum as well as the base64 encoded version of the
content.

\begin{lstlisting}[language=json,caption={DataTransfer.req for NgIniInstall
sent to the CS},captionpos=t]
{
  "vendorId": "se.chargestorm",
  "messageId": "NgIniInstall",
  "data": "{
    \"hash\": \"<SHA256-hash of nanogrid.ini>\",
    \"nanogrid\": \"<Base64 encoded nanogrid.ini>\"
  }"
}
\end{lstlisting}

If the installation succeeded, the station will respond with Accepted.
\begin{lstlisting}[language=json,caption={DataTransfer.conf for NgIniInstall
sent from the CS},captionpos=t]
{
  "status": "Accepted"
}
\end{lstlisting}
If the installation fails, the station will respond with Rejected and a
human readable error in the data part.
\begin{lstlisting}[language=json,caption={DataTransfer.conf for NgIniInstall
sent from the CS},captionpos=t]
{
  "status": "Rejected",
  "data": "{\"reason\: \"<reasoncode>\"}"
}
\end{lstlisting}
where \verb|reasoncode| is:
\begin{description}
\item[hash mismatch]
\item[could not write  to file] Try again after a hard reset. If it still
  doesn't work, it's likely a corrupted flash or file system.
\end{description}



\subsubsection{Retrieve a \nanogrid\ file}
\label{sec:retr-nanogr-file}

To retrieve the \nanogrid\ configuration file, the CSMS shall send:

\begin{lstlisting}[language=json,caption={DataTransfer.req for NgIniRetrieve
sent to the CS},captionpos=t]
{
  "vendorId": "se.chargestorm",
  "messageId": "NgIniRetrieve"
}
\end{lstlisting}
If there is a nanogrid.ini file on the station, the reply will look like:
\begin{lstlisting}[language=json,caption={DataTransfer.conf for NgIniRetrieve
sent from the CS},captionpos=t]
{
  "status": "Accepted",
  "data": "{\"nanogrid\": \"<Base64 encoded nanogrid.ini>\"}"
}
\end{lstlisting}
If there is no nanogrid.ini file, the station will send Rejected.
\begin{lstlisting}[language=json,caption={DataTransfer.conf for NgIniRetrieve
sent from the CS},captionpos=t]
{
  "status": "Rejected",
  "data": "{\"reason\": \"nanogrid.ini does not exist\"}"
}
\end{lstlisting}


\subsubsection{Delete the \nanogrid\ file}
\label{sec:delete-nanogrid-file}


To delete a  nanogrid.ini the CSMS shall send:
\begin{lstlisting}[language=json,caption={DataTransfer.req for NgIniRemove
sent to the CS},captionpos=t]
{
  "vendorId": "se.chargestorm",
  "messageId": "NgIniRemove"
}
\end{lstlisting}
The station will reply with Accepted if it can delete the file.
\begin{lstlisting}[language=json,caption={DataTransfer.conf for NgIniRemove
sent from the CS},captionpos=t]
{
  "status": "Accepted"
}
\end{lstlisting}
and with Rejected if it can't be deleted.
\begin{lstlisting}[language=json,caption={DataTransfer.conf for NgIniRemove
sent from the CS},captionpos=t]
{
  "status": "Rejected",
  "data": "{\"reason\": \"nanogrid.ini could not be removed\"}"
}
\end{lstlisting}
In this case, perform a hard reset and try again. If the error persists, it's
likely a corrupted flash or file system.


\subsection{\nanogrid\ Client Status}
\label{sec:nanogr-client-stat}

These messages are available if \verb|com.ctek.ngclientstatus| is in the comma
separated list of values in the configuration key
\verb|CustomizationCtrlSupported|.

They can be enabled by adding \verb|com.ctek.ngclientstatus| to the
comma separated list in the configuration key
\verb|CustomizationCtrlEnabled|.


\subsubsection{Client status updates}
\label{sec:client-stat-updat}

The \nanogrid\ controller will send a message to inform the CSMS of any
clients that might be offline, as soon as \emph{any} clients on-/offline
status changes.

\begin{lstlisting}[language=json,caption={DataTransfer.req for NgClientStatus
sent from the CS},captionpos=t]
{
  "vendorId": "com.ctek",
  "messageId": "NgClientStatus",
  "data": "{\"NgLostClient\": [\"cbid\",...]}"
}
\end{lstlisting}
where \verb|NgLostClient| is a JSON array with the \verb|ChargeBoxId| of all
configured charging stations that the \nanogrid\ controller considers offline.

The CSMS is expected to reply with \verb|Accepted|.
\begin{lstlisting}[language=json,caption={DataTransfer.conf for NgClientStatus
sent to the CS},captionpos=t]
{
  "status": "Accepted"
}
\end{lstlisting}


\subsubsection{Triggering a client status update}
\label{sec:trigg-client-stat}

The CSMS can trigger a client status update, by sending:

\begin{lstlisting}[language=json,caption={DataTransfer.req to trigger an
NgClientStatus. This trigger message is sent from the CSMS.},captionpos=t]
{
  "vendorId": "com.ctek",
  "messageId": "NgClientStatus"
}
\end{lstlisting}
Or with an empty \verb|data| object:
\begin{lstlisting}[language=json,caption={DataTransfer.req  to trigger an
NgClientStatus. This trigger message is sent from the CSMS.},captionpos=t]
{
  "vendorId": "com.ctek",
  "messageId": "NgClientStatus",
  "data": ""
}
\end{lstlisting}

The CS will reply with:
\begin{lstlisting}[language=json,caption={DataTransfer.conf for the trigger
version of NgClientStatus sent from the CS},captionpos=t]
{
  "status": "Accepted"
}
\end{lstlisting}
if the CS accepted the trigger message and has queued a real
\verb|NgClientStatus| message to be sent.

The failure replies are:
\begin{lstlisting}[language=json,caption={DataTransfer.conf for the trigger
version of NgClientStatus sent from the CS},captionpos=t]
{
  "status": "Rejected",
  "data": "errorMsg"
}
\end{lstlisting}
where \verb|errorMsg| can be either of:
\begin{description}
\item[NonHandledData] there was a non-empty \verb|data| element in the
  request.
\item[Disabled] the \verb|DataTransfer.req| hasn't been enabled on this
  \nanogrid\ controller. See the introduction of
  section~\ref{sec:nanogr-client-stat} for information on how to enable the
  \verb|DataTransfer.req|.
\item[No NanoGrid present] this isn't a \nanogrid\ controller, thus this
  \verb|DataTransfer.req| isn't available.
\end{description}


\subsection{Client FW upgrades from a \nanogrid\ controller}
\label{sec:client-fw-upgrades}

Certain \nanogrid\ controllers can distribute FW files for different types of
clients. To make the CSMS aware of this capability, these \nanogrid\
controllers adds \verb|com.ctek.ng.fw| to\\
\verb|CustomizationCtrlSupported|.

\subsubsection{Download and distribute FW files}
\label{sec:downl-distr-fw}

To ask the \nanogrid\ controller to download and distribute a FW file, use the
following command:
\begin{lstlisting}[language=json,caption={DataTransfer.req for download of FW
files sent to the CS},captionpos=t]
{
  "vendorId": "com.ctek",
  "messageId": "NgFirmwareDownload",
  "data": "{
    \"location\": \"URL\",
    \"hash\": \"<MD5-hash of the FW file>\"
  }"
}
\end{lstlisting}

The controller will respond with:
\begin{lstlisting}[language=json,caption={DataTransfer.conf for download of FW
files sent from the CS},captionpos=t]
{
  "status": "Accepted"
}
\end{lstlisting}

\subsubsection{Notification of download/parsing progress}
\label{sec:notif-downl-progr}

Once the \nanogrid\ controller starts to download the FW file, it will send a
status notification for each step of the process, informing the CSMS about the
progress and / or any failure.
\begin{lstlisting}[language=json,caption={DataTransfer.req for reporting
the progress status of the FW file download sent from the CS},captionpos=t]
{
  "vendorId": "com.ctek",
  "messageId": "NGFirmwareStatusNotification",
  "data": "{
    \"status\": \"<status>\"
  }"
}
\end{lstlisting}
Where the \lstinline{<status>} can be either one from:
\begin{description}
\item[Downloaded] The FW file was downloaded.
\item[DonwloadFailed] The FW file couldn't be downloaded.
\item[Downloading] Actively downloading a FW file.
\item[Idle] Not doing anything.
\item[HashMismatch] The hash doesn't match.
\item[MissingMetaData] The meta data is missing from the FW file.
\item[UnknownClientType] The FW files meta data points to an unknown type of clients.
\item[Published] The FW file is now actively being used to update clients.
\end{description}

The CSMS shall acknowledge the receipt of the status notification by:
\begin{lstlisting}[language=json,caption={DataTransfer.conf for reporting the
progress status of the download of FW file download sent to the CS},captionpos=t]
{
  "status": "Accepted"
}
\end{lstlisting}

\subsubsection{Remove FW files}
\label{sec:remove-fw-files}

The CSMS can also request tho \nanogrid\ controller to remove one or all FW
files. This is done by:
\begin{lstlisting}[language=json,caption={DataTransfer.req to remove a FW
file sent to the CS},captionpos=t]
{
  "vendorId": "com.ctek",
  "messageId": "NgFirmwareRemove",
  "data": "{
    \"clientType\": \"\[<clientType\]\"
  }"
}
\end{lstlisting}
Where \lstinline{<clientType>} can be:
\begin{description}
\item[CCU] For CCU based charging stations / clients.
\end{description}

The cardinality of \lstinline{<clientType>} is \lstinline{0..*}, i.e.\ it's an
array of 0 or more elements. If the array is empty, the whole \lstinline{data}
field can be omitted. That would correspond to a request to remove all types
of FW files currently being offered by the \nanogrid\ controller.

The reply looks like:
\begin{lstlisting}[language=json,caption={DataTransfer.conf to remove a FW
file, sent from the CS},captionpos=t]
{
  "status": "Accpted",
  "data": \"<status>\"
}
\end{lstlisting}
Where \lstinline{<status>} is:
\begin{description}
\item[Accepted] The removal request has been accepted.
\item[UnknownType] Removal of FW file for an unknown client type was requested.
\end{description}

\section{Extended Authentication}
\label{sec:extend-auth}


The availability of the messages in this section is seen by
\verb|se.chargestorm.extendedauth| in
\verb|CustomizationCtrlSupported|. However, they need to be activated by
adding\\ \verb|se.chargestorm.extendedauth|  to the comma separated list in
\verb|CustomizationCtrlEnabled|.

\subsection{Introduction}
\label{sec:introduction}

The messages defined here are used to allow e.g.\ an RFID-token to be valid
only for a single EVSE (connector) and not for the whole charging
station. That's a functionality that was missing from OCPP 1.6.


\subsection{Authorize request}
\label{sec:authorize-request}

\begin{lstlisting}[language=json,caption={DataTransfer.req for
AuthorizeExtendedRequest sent from the CS},captionpos=t]
{
  "vendorId": "se.chargestorm",
  "messageId": "AuthorizeExtendedRequest",
  "data": "0,<idToken>
}
\end{lstlisting}
where \verb|<idToken>| is the \verb|idToken| type from the regular
\verb|Authorize.req|, eg.\ \verb|"data": "0,D300A6B2"| for a RFID tag
\verb|0xD300A6B2|.

\begin{lstlisting}[language=json,caption={DataTransfer.conf for
AuthorizeExtendedRequest sent to the CS},captionpos=t]
{
  "status": "Accepted",
  "data": "<evseId>,<AuthorizationStatus>"
}
\end{lstlisting}
where \verb|<evseId>| is the EVSE the \verb|idTag| is valid for. Use 0 for the
whole charging station. \verb|<AuthorizationStatus>| is the same as in a
regular \verb|Authorization.conf|.


\subsection{Start transaction}
\label{sec:start-transaction}

\begin{lstlisting}[language=json,caption={DataTransfer.req for
ExtendedStartTransactionRequest sent from the CS},captionpos=t]
{
  "vendorId": "se.chargestorm",
  "messageId": "ExtendedStartTransactionRequest",
  "data": "<payload>"
}
\end{lstlisting}
where the \verb|payload| is identical to a regular
\verb|StartTransaction.req|, only that it is passed in a string.

The response is:
\begin{lstlisting}[language=json,caption={DataTransfer.conf for
ExtendedStartTransactionRequest sent to the CS},captionpos=t]
{
  "status": "Accepted",
  "data": "{
    \"idTagInfo\": \"\",
    \"transactionId\": integer,
    \"AuthorizedEvseId|": integer
  }"
}
\end{lstlisting}
where \verb|idTagInfo| is the same as in OCPP 1.6.
\verb|AuthorizedEvseId| is an integer stating whether the \verb|idTag| in the
request is valid for the whole station (0) or a single EVSE (>0). This will be
stored in the cache if it's enabled.


\subsection{Stop transansaction}
\label{sec:stop-transansaction}

\begin{lstlisting}[language=json,caption={DataTransfer.req for
ExtendedStopTransactionRequest sent from the CS},captionpos=t]
{
  "vendorId": "se.chargestorm",
  "messageId": "ExtendedStopTransactionRequest",
  "data": "<payload>"
}
\end{lstlisting}
where the \verb|payload| is identical to a regular
\verb|StopTransaction.req|, only that it is passed in a string.


The response is:
\begin{lstlisting}[language=json,caption={DataTransfer.conf for
ExtendedStopTransactionRequest sent to the CS},captionpos=t]
{
  "status": "Accepted",
  "data": "{
    \"idTagInfo\": \"\",
    \"AuthorizedEvseId|": integer
  }"
}
\end{lstlisting}
where \verb|idTagInfo| is the same as in OCPP 1.6.
\verb|AuthorizedEvseId| is an integer stating whether the \verb|idTag| in the
request is valid for the whole station (0) or a single EVSE (>0). This will be
stored in the cache if it's enabled.




\subsection{Send local list}
\label{sec:send-local-list}

\begin{lstlisting}[language=json,caption={DataTransfer.req for SendLocalList
sent to the CS},captionpos=t]
{
  "vendorId": "se.chargestorm",
  "messageId": "SendLocalList",
  "data": "{
    \"listVersion\": integer,
    \"updateType\": UpdateType,
    \"localAthorizationList\": [
      {
         \"idTag": \"<idTag>\",
         \"idTagInfo\": {
            \"status\": AuthorizationStatus,
            \"parentIdTag\": \"<IdToken>\",
            \"evseId\": integer,
         }
      },
     ...
    ]
  }"
}
\end{lstlisting}
where \verb|evseId| is an integer, describing which EVSE the \verb|idTag| is
valid for. Range $0-2$.
\verb|idTagInfo|, \verb|parentIdTag|, and \verb|evseId| are all optional,
which is similar to the regular \verb|SendLocalList.req|. Thus, the
\verb|data| element is almost a copy of the payload for
\verb|SendLocalList.req|. 

The CS will respond with status Accepted if everything can be parsed
correctly.
\begin{lstlisting}[language=json,caption={DataTransfer.conf for a successful
SendLocalList sent from the CS},captionpos=t]
{
  "status": "Accepted"
}
\end{lstlisting}

If there's a version mismatch, the CS will repond with
\begin{lstlisting}[language=json,caption={DataTransfer.conf for a failed
SendLocalList sent from the CS},captionpos=t]
{
  "status": "Rejected",
  "data": "{
     \"reason\": \"VersionMismatch\",
     \"currentVersion\": integer
  }"
}
\end{lstlisting}

            \"expiryDate\": \"<date>"
         }
      },
     ...
     ]
  }"
}
\end{lstlisting}
